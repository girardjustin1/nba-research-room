# Independent audit, round 2: models and in-app notifications

Date: October 8, 2026. Scope: this checkout and its cleaned DuckDB store. Read the October 5 audit first; the baseline F04/F18 fixes are not re-reported as defects.

**CONFIRMED** means reproduced by a benchmark, data check, or executable counterexample. **SUSPECTED** means a reasoned concern whose occurrence or effect was not reproduced. Synthetic notification fixtures establish mechanisms, not their frequency in the real account. The real notification, status-event, matchup-snapshot and Yahoo tables are intentionally empty.

## 1. Summary

1. **The reported bake-off numbers reproduce, but the challengers do not get an equivalent teammate adjustment.** LightGBM's shared fitting code removes every DNP before fitting that adjustment; Ridge and CatBoost inherit it. An identity-correction control still changes 477,396 validation prediction rows. This is a training defect, not test-season leakage.
2. **Keeping the baseline is defensible; saying history-based models or blending cannot improve it is too broad.** The inverse-error ensemble loses MAE on nine of ten stats as reported, but improves RMSE on all ten. A validation-only optimized convex blend finds small steals/turnovers gains, chooses the baseline for five stats, and fails on free throws. There is no demonstrated across-the-board replacement.
3. **Notification impact can be missing, stale, or attached to the wrong news.** The pipeline's start-time cutoff excludes its newly created snapshot. Independently, the global latest-two-snapshots query can compare different weeks/opponents and attach the same change to every affected player.
4. **The inbox can lose read state and show stale urgency or unread counts.** Concurrent JSON updates lose successful marks; the read endpoint still fails while another process holds the DuckDB writer. The bell's hook does not actually reload on League navigation. Repeated status episodes, expired games, and the scheduler's first-tip cutoff also have reproducible failures.
5. **Regression checks are encouraging but not fully green.** `make test`: **292 passed, five Chrome-startup errors**, no assertion failures. F04 rejects invalid rosters; the baseline has zero FGM>FGA or FTM>FTA cases in 40,919 test rows. New challenger corrections nevertheless produce FTM>FTA, including 56 ensemble rows. Web dependencies are absent, so TypeScript/Vitest could not run. No reviewed notification path acts inside Yahoo.

Method: all created files, caches, temporary stores, and evidence are under `audit/`; production source, tests, configuration, jobs, web files and the supplied database were not edited. Real-store connections in the audit are read-only; mutation probes use in-memory or `audit/` stores. `git diff` is empty; `git status --short` lists only `audit/`. No feeds were contacted and no dependencies were downloaded.

### Model nesting, fairness and mathematical checks

**No new test-outcome path was found in the bake-off's fit/weight split.** Stage 1 fits 2023–24 and takes weights from 2024–25 only. Stage 2 refits 2023–25 and evaluates 2025–26. The validation weights are frozen before stage 2. A real-data tamper setting every 2025-season game outcome to zero leaves the entire earlier feature table unchanged. Truncation before January 1, 2025 leaves 60,163 earlier input rows identical. Altering the outcomes of one 35-row game leaves that game's input features unchanged, including teammate priors. Historical outcomes from *earlier* games within a test season appropriately update later pre-game states; this is rolling forecasting, not a season-opening forecast.

Teammates-out learns from actual historical absences within the supplied training seasons; that is legitimate supervised information. At prediction it uses `1−p_play`, not test `y_did_play`. A01 is about removing absences from the challenger training population. `y_teammates_out_usage` remains excluded from the feature allowlist, so round-one F11 stays fixed.

**OOF nuance:** with one season, `LgbmModel.fit` explicitly uses in-sample corrections for phi. It does not sneak in the validation/test season to obtain a second fold. Consequently stage-1 phi is not OOF, despite the general docstring. This affects uncertainty estimates, not the MAE-only ensemble weights. With two seasons it uses leave-one-season-out corrections for phi, including training on the later *training* season when correcting the earlier one. That is not a forward-only historical validation scheme, but neither fold contains 2025–26 test outcomes. Ridge and CatBoost inherit this behavior.

All five members predict exactly the same **40,457 validation / 40,919 test player-game keys**, twelve stat rows each, without duplicates or non-finite means/SDs. Their P(plays) values are identical. Scoring and paired error alignment are common across models. Models intentionally use different transformations/subsets of the same information; A01 is the substantive comparison asymmetry. The bake-off matches `scoreboard.evaluate`'s per-game protocol. It is not a weekly fantasy-win backtest or a schedule-expanded live forecast evaluation; absent box-score rows cannot enter this population. Preseason projections and news/market overlays are not supplied.

Two test rows and thirteen validation rows have `y_did_play=False`, zero minutes, but nonzero box-score stats. `score` uses their stored outcomes rather than explicitly setting all stats to zero. Thus “a sat game counting 0” is not literally universal. These may be short appearances rounded to zero or source inconsistencies; raw API bodies are unavailable. Rows are preserved in `stage*_zero_minutes_nonzero_stats.csv`. This is a disclosed data-quality exception shared by all models, not evidence of unequal scoring.

**Hierarchical implementation:** priors are training-only aggregate stat totals divided by training minutes, by first-letter G/F/C; unknown/missing positions fall back to the overall league rate. The evidence quantity is the baseline's capped prior-games × pre-game minutes. Each k is chosen on the supplied training rows by squared error conditional on actual minutes. This uses in-sample empirical-Bayes tuning rather than an inner temporal validation set, but no test targets. The overridden `shrunk` is indeed invoked at prediction despite `shrink=False`: prediction exactly matches an explicit manual-shrink-then-baseline calculation (maximum mean difference 0). All eleven rates change in the probe. Phi is inherited from the unshrunk baseline before these priors are fitted, so hierarchical SDs are not separately recalibrated to its final mean. Today's coarse position is a reasonable disclosed proxy for live use; A07 is the narrower historical-metadata limitation.

**Ensemble algebra/alignment:** for valid inputs it computes `Σw μ / Σw` and `Σw[σ²+(μ−μ_blend)²] / Σw`. This is the variance of a mixture distribution, as documented, not the variance of an average of independent model predictions. Reversing member row order gives correct keyed means **[13, 27.5]** and variances **[7, 22.75]**. A genuinely absent member row is locally renormalized; no positional alignment bug occurred in the bake-off. NaNs are a different case (A06). Mixture moments plus a normal 80% band do not by themselves guarantee calibrated mixture quantiles.

The game-day bootstrap is actually paired and resamples complete days: 1,000 draws, fixed seed 0, 168 test dates. It preserves within-day dependence, but does not establish independence across dates, adjust for all model/stat comparisons, or account for historical development on this season. “Test touched once” describes this job's control flow; it does not undo the earlier model-development reuse already documented in round-one F14. That old concern is not presented as a newly discovered defect.

### A better-specified blend, checked without editing production

I solved the **validation MAE** convex problem separately for each displayed stat: nonnegative weights summing to one, using all 40,457 validation rows and no test targets. A second variant enforces a *final* 5% lower bound on every weight. Optimization uses an explicit linear program (`scipy.optimize.linprog`); every solve succeeded. Saved stage-2 predictions are then scored once with those fixed weights. The two variants are diagnostic experiments, not a fresh untouched confirmatory test.

This is a fairer test of whether a convex combination can reduce the chosen loss because it accounts for how member errors combine. The inverse-error rule in the build prompt is a legitimate recipe to test, but cannot answer that broader question. The floor also excludes the baseline-only solution and forces dilution even when validation prefers it. Validation residual correlations are indeed high: points **0.98467–0.99965**, all displayed stats **0.93004–1.0**. High correlation alone does not mathematically preclude a useful small blend.

Train the blend on chronological validation folds, permit zero weights, constrain coherent stat lines, calibrate its uncertainty separately, and predeclare the adoption rule. Keep an untouched later evaluation period. The current means and fantasy simulations make reporting RMSE/calibration alongside MAE especially relevant.

### Notification rules and contract checks

The status matrix matches the documented priority policy **at generation time**: my active Out/Out For Season/Doubtful player is urgent before tip; the same hard status on BN/IL/IL+ is high; Questionable and Day-To-Day are normal. A minutes cap also triggers an alert even without a limiting status. Probable/Available without a cap do not. Opponent injury news is normal. Game-day and model notes use `low`, which is a valid fourth frontend priority. Injury urgency is not restricted to three hours; that window applies only to lineup reminders.

The lineup reminder's own boundary check is correct: none 181 minutes before first lock; one at −180 and −1 minutes; none at or after lock. It requires a changed slot with an optimal player and names up to three changes. Opponent lookup uses the current configured fantasy week and my team, returning team 5 in a synthetic matched-week check and no opponent when the other week has no data. It does not pick an arbitrary roster. Current roster/position data is not an as-of history, and pre-game does not refresh Yahoo rosters; actual same-day ownership freshness cannot be measured here.

[alert_contract_checks.json](alert_contract_checks.json) verifies response and item field sets against `SeasonNotification`/`NotificationsResponse`, including nullable player/impact/action/deadline/claim, provenance and unread count; synthetic JSON contains no NaN. Impact/category-delta and player objects reuse the season API shapes. `claim=null` correctly reflects that waiver claim statuses are not implemented. There is no observed field-name mismatch. This manual/runtime contract check does not replace TypeScript or React integration tests.

Serial marks work: unread **4 → 3 → 0** after mark-one/mark-all; a later-created notification becomes unread **1**. Empty/omitted IDs intentionally mean mark-all. The concurrency failures are separate. The UI currently exposes mark-all and navigation actions; clicking an alert does not call mark-one. `notificationActions.ts` routes only within the app and discards date/move references, so an old card navigates to the current generic screen rather than its exact dated recommendation. Demo transport's local read flags and reset logic are consistent by inspection; a full demo UI run was not possible.

## 4. Not verifiable with this data

- **Real notification usefulness, false-alert rates, causal impact and timing.** `notifications`, `status_events`, `matchup_snapshots`, all `yahoo_*`, `projections` and `api_responses` contain zero rows intentionally. The impact/roster/timing findings use labeled synthetic fixtures. We cannot claim these failures occurred in this user's live league, measure missed alerts, or verify whether a real snapshot delta came from a particular injury.
- **Trade and ownership freshness.** There is no usable real Yahoo history in this copy, and current `players` is not a dated transaction or position history. The trade reproduction demonstrates cross-game attribution, not its prevalence. A07 and B10 remain suspected for their real historical/parsed-news effects.
- **Licensed/preseason, market and draft behavior.** `external_projections`, `props_ladder`, all `draft_*`, and live `projections` are empty by design. These data are not required for the requested history-only bake-off, but its results say nothing about the live blended/news/market forecasting stack or draft decisions. The raw store retains 138,296 game logs, 104,756 advanced-stat rows and 21,633 NBA-report player rows.
- **A repaired challenger ranking.** A01 is reproduced with an identity control and real historical data; I did not silently repair production fitting and present a new ranking as the original bake-off. How the corrected LightGBM/CatBoost/Ridge frame would rank, and its weekly fantasy utility, still needs an explicit rerun after a fix.
- **Full web behavior and browser integration.** No node modules are installed; TypeScript and Vitest could not execute offline. B09 has a production-hook-body lifecycle reproduction with a small hook harness, not a mounted React or browser test. The five Python test errors are also browser startup limitations, not evidence those listener behaviors passed.
- **A new independent season or full round-one re-audit.** The scratch blend uses the already inspected test season only for evaluation, so it is exploratory evidence. `make test` and targeted F04/F18/F11/feature-causality checks are not a rerun of every old replay, market benchmark or historical calibration study. The known one-game-stale state for a player who never appears again remains previously disclosed, not a new finding.

## 5. Looked wrong but turned out fine

- **Building all three seasons before slicing does not itself leak future outcomes.** The shifted player histories and teammate priors survived both truncation and same-game/future-season outcome tampering. No label path from the test season into stage-1 weights was found.
- **One-season OOF fallback does not borrow a later season.** It is an in-sample phi fit, with the limitations explained above; MAE weights never use phi. Actual test coverage is measured, not inferred from that claim.
- **Hierarchical shrinkage is applied.** `shrink=False` suppresses the baseline's own shrinker; dynamic dispatch still calls `HierModel.shrunk`. The trained position priors/k and manual predictive calculation agree exactly. Fallback to league priors is intentional.
- **The ensemble mixture variance and key alignment are correct for valid, unique rows.** Permuting member rows did not change the result. Its bands are wider partly because that is the requested mixture formula; wider is not automatically better calibrated.
- **Core serial notification contracts work.** Normal status priority choices, Eastern dates, matched-week opponent lookup, the reminder's three-hour boundary, the ≥0.02 waiver threshold, local serial read marks and response field names are consistent. Failures concern integration, persistence under concurrency and alert lifecycle, not fabricated engine arithmetic.
- **The round-one baseline fixes remain in place.** Actual solver output is feasible; an invalid returned solve is rejected before scoring. Baseline makes never exceed attempts on the held-out set. The realized teammate-absence field remains a `y_` target excluded from features.
- **Nothing in the reviewed notification paths writes to Yahoo.** The alert generators write local notifications; read actions write only local JSON; frontend actions navigate within the app. The pipeline's Yahoo integration reads/imports snapshots through the read-method allowlists in `ingest/yahoo_api.py:32` and `:70`; recommendation/optimization calls do not execute transactions. The existing Yahoo write-blocking tests passed in `make test`. No live Yahoo request was made during this audit.
